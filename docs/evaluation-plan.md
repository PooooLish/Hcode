# Hcode Agent 能力评测计划

## 目标

建立一套可重复、可比较且不依赖主观演示的测试，衡量 Hcode 是否能正确完成真实仓库任务。现有 pytest 继续验证程序实现，评测集单独衡量 Agent 的任务能力。

## 第一阶段任务集

首版使用 20～30 个小型、可离线复位的仓库任务：

| 类别 | 示例 | 主要判定 |
| --- | --- | --- |
| 理解 | 定位失败原因并给出证据 | 文件、行号和原因正确 |
| 单文件修改 | 修复明确缺陷 | 隐藏测试通过，无无关修改 |
| 多文件修改 | 同步接口、实现和测试 | 全部验收测试通过 |
| 工具恢复 | 命令失败或输出截断 | 能修正策略并继续 |
| 权限安全 | 请求危险操作 | 正确阻断或请求批准 |
| 长上下文 | 中途压缩后继续任务 | 约束和未完成步骤保留 |
| 会话恢复 | 中断后恢复 | 状态、文件和目标一致 |
| 协作 | 子 Agent 分工与汇总 | 结果完整且无冲突 |

每个任务固定：初始仓库快照、任务提示、模型与参数、预算、允许工具、超时、验收测试和禁止修改范围。

## 指标

- `task_success`：最终验收测试是否全部通过。
- `pass_at_1`：首次独立运行成功率。
- `unrelated_diff`：验收范围外的修改文件数和行数。
- `permission_violation`：未获授权的写入、命令或网络尝试次数。
- `tool_calls`：总工具调用数及失败调用数。
- `latency_seconds`：首响应与总完成时间。
- `input_tokens`、`output_tokens`、`estimated_cost`。
- `context_recovery`：压缩或恢复后必须保留的信息命中率。

## 对比原则

Hcode、tricoder-cli 和候选基线工具使用相同模型、提示、任务快照、权限范围、Token 预算、超时和验收脚本。每个任务至少独立运行三次，原始事件保存为 JSONL，汇总报告记录失败类型而不仅是平均分。

## 通过门槛

第一版公开结果必须满足：

- 全部任务可由脚本复位和验收。
- 报告能从原始事件重新生成。
- 费用和失败不会被静默忽略。
- 不保存模型密钥或私有仓库内容。
- 结论明确标注模型、日期、样本量和限制。

## 计划产物

```text
evals/
  cases/              固定任务定义
  fixtures/           可复位的最小仓库
  runners/            Hcode 与基线适配器
  validators/         验收脚本
  reports/            脱敏后的汇总结果
```
